# hiddify-core, ветка `hardened`: изменения форка

Основа: hiddify-core v5.9.8 (`6777b7f`), hiddify-sing-box `9dbf55dde`, ray2sing `6974ad6`.
Все подмодули с правками — на ветках `hardened`: `hiddify-sing-box`, `ray2sing`,
`hiddify-sing-box/replace/amneziawg-go` (влит апстрим v3.1.20261116), `hiddify-sing-box/replace/sing`.
Номера HC-xx и P-xx — находки внутреннего аудита (он не публикуется). Хеши коммитов ниже — из истории
разработки до публикации; если при публикации история пересобиралась (обезличенный автор), в этом
репозитории этих хешей может не быть. Подмодули с правками публикуются как отдельные репозитории
(см. `.gitmodules` здесь и в `hiddify-sing-box`).

Тесты форка лежат рядом с кодом (`hardened_*_test.go`, `h_*_test.go`) и добавлены в git принудительно
(`.gitignore` апстрима исключает `*_test.go`).

## Локальные порты и управление (утечка A, заметность)
- Clash API без TCP-порта; на desktop только по `clash-api-listen` (случайный порт, секрет 32 байта, CORS только свой origin). Секрет сравнивается за постоянное время. (HC-04, HC-35)
- Локальный mixed-прокси: на мобильных в VPN-режиме не создаётся никогда; всегда с паролем (свой или случайный на процесс, нейтральное имя); SOCKS5 UDP ASSOCIATE выключен (`disable_udp` в форке); только 127.0.0.1 на мобильных; `mixed-port: 0` — свободный порт; RPC `GetLocalProxyInfo`; realm 407 — `proxy`. LAN-раздача только с паролем ≥ 8. (HC-17)
- gRPC: режимы без аутентификации запрещены на Android/iOS, на desktop — только с секретом ≥ 32; unix-сокеты (`unix:`, `unix-abstract:`/`@`, проверка `SO_PEERCRED`), свободный TCP-порт, `GetListenAddress`; нейтральный сертификат ECDSA (без «Hiddify, Inc.»). (HC-05, HC-08)
- pprof — только сборка с тегом `with_pprof` (и в libbox); debug не от уровня логов. (HC-07)

## Секреты и данные
- `SetupRequest.data_path`: данные ядра во внутреннем каталоге (на Android по умолчанию `base_path`), umask 077, миграция и удаление старого `<working_dir>/data`; `current-config.json` не пишется (кроме тега `with_debug_files`). (HC-06)
- Логи для приложения очищаются от ссылок, UUID, ключей, паролей, адресов (адреса — кроме уровней debug/trace); конфиг и настройки не логируются; AWG/WG не пишут ключи; ray2sing не печатает профиль. (HC-15)

## Утечка B
- `per-app-proxy-mode`/`per-app-proxy-list`/`per-app-strict`: список в TUN и первыми правилами — отбрасывание потоков TUN с неизвестным владельцем и не той стороны списка (Android 10+). В форке — элемент правила `user_id_range`.

## Собственные сокеты ядра на Android (запрос приложения R1, H-02)
- В VPN-режиме на Android `auto_detect_interface` включён: каждый сокет диалеров sing-box (TCP, UDP Hysteria2/TUIC/QUIC/WireGuard/AWG, DNS, `direct`) защищается `VpnService.protect` через платформу и привязывается к сети по умолчанию; Psiphon — через `DeviceBinder`. `Mobile.protectsOwnSockets()` = true: приложение остаётся внутри своего VPN, его запросы идут через туннель, петли нет. В режиме include строгий фильтр не отбрасывает собственный uid приложения.

В форке: `exclude_types`, `on_demand_types`, `retest_on_network_change`, `disable_ipinfo`, AWG `keepalive_on_use`. (HC-09, HC-10, HC-39)

(HC-13, HC-14, HC-34, HC-38)
- Случайные адреса TUN (`tun-address-seed`). (HC-32)

## Исправления по проверке 5.9.8-sp.3 и desktop (5.9.8-sp.4)
- Шлюз рукопожатий (форк `handshake_gate`): TLS-дозвоны выходов (TLS-дайлер, VLESS, XHTTP, gRPC) берут очередь сервера до TCP-соединения и держат её до конца рукопожатия; сервер — это адрес (подсеть), а не пара (адрес, SNI); каждый ClientHello к адресу — не раньше `min_gap` после предыдущего. Итог: не больше 3 открытых незавершённых рукопожатий к адресу и ≥ 450 мс между ClientHello.
- Обращения к собственным подсетям TUN (/30 и /126) не выходят с устройства: DNS на порт 53 отвечает ядро, остальное сразу отклоняется — раньше при обходе LAN они уходили через direct на физическую сеть (например, системная DoT-проба адреса DNS туннеля), а без обхода — на сервер. Доступ к локальной сети остаётся.
- keep top управляет только членами автогрупп: число не больше размера автогруппы, узлы «по требованию» не ждут первого пинга (не было ложных «KEEP TOP N outbounds have no result»).
- Загрузка rule-set, оборванная пересборкой туннеля, — не ошибка: повтор с нарастающей паузой и немедленная загрузка после перезапуска (форк); в журнале — debug/warn вместо error.
- После горячей перезагрузки старый пинг узла «по требованию» (не в циклах проверки) показывается как ожидающий, а не как свежий (форк).
- Windows: свои имена — запускатели `SandpiperCore.exe`, `SandpiperAdmin.exe`, `SandpiperCoreEngine.exe` (Makefile, VERSIONINFO), служба `SandpiperAdminBG` («Sandpiper Service»), её адаптер `SandpiperAdminBg`, данные и секрет в `ProgramData\Sandpiper\AdminBgService` (Linux: `/var/lib/sandpiper-admin-bgservice`), без обращения к каталогам апстрима. На macOS ярлык, каталоги и фиксированный порт службы (18420) пока прежние (зависят от бандла приложения).

- Desktop без фиксированных портов (рядом с запущенным Hiddify, у которого 17078/17079/18020/18021): ядро в процессе приложения и процесс движка (`core`) слушают свободный порт `127.0.0.1:0` (экспорт библиотеки `getListenAddress`, строка `HIDDIFY_CORE_LISTEN` процесса), mTLS как прежде. Служба VPN-режима Windows/Linux при каждом старте берёт свободный порт и новый сертификат (ключ только в памяти), публикует адрес и сертификат в `control.endpoint` рядом с `control.secret` (пишет только SYSTEM/администраторы/root, читают пользователи) и удаляет при остановке; клиенты (консольный запускатель, ядро приложения, приложение) доверяют только этому сертификату, секрет уходит только по TLS. Служба AppImage — свободный порт и сертификат в выводе (`HIDDIFY_SERVICE_LISTEN`, `HIDDIFY_SERVICE_CERT`).
- Имена и пути связки приложение ↔ ядро ↔ служба — в одном месте (`v2/hcore/vpnservice`); приложение держит те же значения и сверяет их тестом.
- Защита API службы: без секрета служба не работает; каждый установщик пишет новый секрет (новым файлом); каталог `ProgramData\Sandpiper` и каталог службы создаются только установщиком или службой, владелец — Администраторы, защищённый DACL (SYSTEM и Администраторы — полный доступ, Пользователи — только просмотр каталога); чужой каталог отодвигается, не используется; без «моста» (старт без конфигурации приложения отклоняется); движок службы не принимает из запроса `enable-full-config` и `log-file`.
- Строка ошибки, возвращаемая библиотекой desktop, больше не освобождается до чтения (приложение получало мусор вместо причины ошибки запуска); все строки освобождает вызывающий через `freeString`.
- `run` (CLI): Clash API только по `clash-api-listen` (127.0.0.1, свободный порт, секрет), мониторинг групп сохраняется, подписка загружается с User-Agent приложения.
- Неудачная авторизация SOCKS/HTTP на локальном прокси не пишет в журнал присланные имя, пароль и `Proxy-Authorization` (форк `sing`), только факт и адрес источника.

### 5.9.8-sp.4 — финальные правки (проверка маршрутов VPN и рукопожатий на эмуляторе)
- Шлюз рукопожатий: одно незавершённое рукопожатие к серверу за раз, пауза перед каждым ClientHello выбирается заново равномерно в 0,7–1,1 с (раньше всегда 450 мс), не больше 4 новых рукопожатий к серверу за любые 5 с. Значения — в одном месте (`v2/config/builder.go`, `handshakeGate`), с обоснованием; ключи `handshake-gate-max` и `handshake-gate-gap-ms` по-прежнему заменяют число и наименьшую паузу. В форке у `handshake_gate` новые поля `max_gap`, `window`, `window_max` (без них — прежнее поведение).
- После пересборки туннеля (смена настройки TLS и т. п.) узлы «по требованию», не выбранные группой, больше не проверяются: раньше все заменённые узлы проверялись разом — пачка рукопожатий к серверу и пинги у узлов вне автогруппы (форк).
- Датаграмма на адрес DNS туннеля не на порт 53 — не DNS-запрос: идёт по правилам маршрутизации (подсеть TUN отклоняется), без строки ERROR в журнале на каждую; неразбираемый DNS-запрос — warn не чаще раза в минуту, остальное debug (форк).
- Старт ядра без приложения (`Mobile.Start`: «Постоянная VPN», перезапуск после гибели процесса, сторож) строит ядро в контексте `Setup` с интерфейсом платформы. Раньше без него «локальный» DNS был резолвером Go, который на Android спрашивает `[::1]:53` и получает отказ: после возврата туннеля без приложения не разрешались прямые сайты («Россия напрямую»), а проверки узла AmneziaWG падали на DNS.
- Неудачная авторизация на HTTP-части локального прокси не пишет в журнал присланное имя пользователя (форк, `transport/http`).

## 5.9.8-sp.5: выбор узла по рейтингу сервера
- Ключ настроек `tier-policy` (`policy`, `probe-host`, `probe-path`): политика сервера подписки — упорядоченные уровни узлов (`auto`, `fallback`, `last-resort`, `manual`), у узла три оценки 1–5 (надёжность, маскировка, безопасность) и подписи-ключи; формат v1 и строгий разбор — пакет `v2/tiered` (`Parse`, `Bind`: ссылка на узел — номер, с которого начинается имя, или точное имя; двусмысленная или ненайденная ссылка не применяется). Политика без уровней или без единого найденного узла — всё как раньше.
- Построитель (`v2/config/tier_group.go`): при политике — селектор `tiered` из узлов неручных уровней (в порядке выбора), первым в `select` и выбор `select` по умолчанию; тег `tiered` в профиле зарезервирован. Автогруппы `lowest`/`balance`, мониторинг и узлы — без изменений; в hiddify-sing-box ничего не менялось.
- Контроллер (`v2/tiered/controller.go`, `v2/hcore/tiered_runtime.go`) работает, пока в `select` выбран `tiered`: идёт сверху вниз по уровням, проверяя узел передачей 64 КиБ через него (TLS к хосту подписки и тестовому пути, без выбора узла); при остановке передачи или отсутствии ответа у TCP-узла — одна проверка пути до сервера (`DpiProbe`, одно соединение): если TCP к серверу замирает или режется — сразу к UDP-уровням, не перебирая TCP. Понижение — после подтверждённого отказа (`fail` проверок подряд с паузой `retry`), возврат — редкой фоновой проверкой верхних уровней (не раньше `hold`, пауза `up` удваивается до 4 ч, переключение после двух успешных проверок подряд). `last-resort` с `confirm` не проверяется и не включается без согласия пользователя (`SelectOutbound` группы `tiered`). Без сети ничего не понижается. Отметки отказов хранятся по сети (идентификатор — хеш, без имени сети) 6 ч в базе ядра. Проверки идут по одной, рукопожатия — через шлюз.
- `OutboundGroup.tier_state = 8` (proto, только добавление): JSON-состояние выбора для приложения; состояние ядра при выбранном `tiered` учитывает пинг выбранного им узла. Когда политика приходит впервые, `select` один раз переходит с `lowest` на `tiered`; дальше выбор пользователя хранится как обычно.
